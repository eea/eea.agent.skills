# Plone Backend Developer

## Overview

Implement and debug Plone 6 backend changes in EEA projects. EEA backends are
built and started in different ways depending on the project generation, so
discover the project's build system before running or editing anything.

## Discover the project first

- Read the project `AGENTS.md` for project-specific commands.
- Read the `Makefile` (`make help`) and the build configuration
  (`sources.ini`, `requirements.txt`, `constraints.txt`, or `pyproject.toml`).
- Identify how the dev environment is created and how the app is started.
- Check whether a `develop/` directory exists; if not, the backend is likely
  container-based.

See `references/plone-project-layouts.md` for the known EEA layouts.

## Core workflow

1. Confirm the failing endpoint, request path, and expected behavior.
2. Locate the relevant package in the project's sources list or installed
   add-ons.
3. Reproduce locally; add minimal logging only when needed.
4. Apply the fix in the add-on or configuration.
5. Restart Plone after Python changes; hot reload is not available.
6. Validate with a targeted `zope-testrunner` invocation or manual verification.

## Common tasks

- Add or update a backend add-on and refresh the dev sources with the project's
  develop target.
- Adjust Plone configuration and verify the app starts.
- Investigate errors from the WSGI process and trace back to the relevant add-on
  module.
- Work with REST API behavior used by the Volto frontend; confirm the exact
  endpoint contract before changing serializers.

## Good practices

- Restart Plone after Python changes; use the reload endpoint (`@@reload`) only
  for quick iteration, then restart to confirm.
- Keep changes small and add targeted tests for regressions.
- Prefer configuration and existing add-ons over fork-and-patch.
- Do not edit generated build artifacts; edit sources and re-run bootstrap.

## Repo context

Use `references/plone-project-layouts.md` for the known EEA backend layouts,
commands, and how to discover them.

## Verification

Run the project's targeted test command, typically
`bin/zope-testrunner --test-path sources/<package>` from the dev environment
root, or the equivalent documented by the project. Report what you ran.

## EEA-wide backend policy

### Plone version

EEA projects run Plone 6.x. Read the exact version from the project's pins
(`constraints.txt`, `requirements.txt`, or `pyproject.toml`) instead of assuming.

### Persistence

Production EEA Plone deployments use RelStorage (PostgreSQL) rather than the
default ZODB file storage. When reproducing production behavior, prefer the
project's RelStorage target when it exists.

### Release and CI

Backend releases and quality gates run through Jenkins. See `jenkins-pipeline`,
`code-quality`, and `testing` for the CI contract and command parity.

## Handoff to other EEA skills

- Frontend/Volto behavior → `plone-frontend-developer`, `volto-cypress-writer`
- CI and quality gates → `jenkins-pipeline`, `code-quality`, `testing`
